# 프로젝트 초기 설정과 일상 개발

이 문서는 셋업 프롬프트를 적용한 프로젝트에서 읽는다. 저장소 설정은 두 셋업 프롬프트, 일상 개발의 진입 절차는 이 문서가 맡는다. 적용 시 프로젝트 작업 문서에 이 절차를 옮기고 실제 경로를 연결한다. 원본의 개인 경로나 다른 프로젝트 값을 복사하지 않는다.

## 처음 한 번: Matt Pocock 스킬 연결

1. 현재 런타임이 선택한 설치 manifest에서 `mattpocock-skills:setup-matt-pocock-skills` 원문과 템플릿을 찾는다. 목록에 없는 스킬도 manifest의 `skills` 경로에서 확인한다. 미설치·미확인은 구분하고 다른 출처의 동명 스킬로 대체하지 않는다. 설치·유료 서비스 활성화는 별도 승인 범위다.
2. 실제 remote·기존 지침·이슈 추적·라벨·도메인 문서를 조사한다. 공식 초기 설정 스킬의 확인·초안·편집 절차를 따른다. 이미 확인한 선택과 승인 범위는 재사용한다.
3. 프로젝트의 `docs/agents/issue-tracker.md`에 실제 추적 위치와 조회·생성·상태 변경·부모/자식·의존성·완료 처리 방법을 기록한다. GitHub remote면 GitHub Issues를 제안하되 기존 GitLab·로컬 Markdown·Jira·Linear 관례를 보존한다. PR을 요청 수집 대상으로 삼는 옵션은 기본 Off다.
4. `triage`가 설치돼 있으면 기존 라벨과 다섯 역할을 대조한다. 기본값은 `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`다. 선택한 매핑만 `docs/agents/triage-labels.md`에 기록하고 승인된 누락 라벨을 만든다. `triage`가 없으면 해당 문서·지침 블록을 생략한다.
5. `docs/agents/domain.md`에 소비 규칙을 연결한다. 기본은 root `GLOSSARY.md`와 `docs/adr/`다. 실제 모노레포 경계가 있을 때만 여러 컨텍스트를 제안한다. 탐색 전에 관련 용어집·ADR을 읽고, 용어집 표현을 사용하며 ADR 충돌을 드러낸다. 없는 도메인 문서는 필요가 생길 때 만든다.
6. `AGENTS.md`의 `## Agent skills` 블록을 갱신한다. 파일이 없으면 `AGENTS.md`를 만든다. 기존 `CLAUDE.md`가 있으면 고유 규칙을 `AGENTS.md`로 옮기고 `CLAUDE.md`는 지운다. 개인·전역 지침은 건드리지 않는다. 중복 블록·새 shim·symlink를 만들지 않는다. 사용하는 런타임이 `AGENTS.md`를 읽는지 확인하고 자동 로딩이 없으면 시작 절차에 명시적 읽기를 연결한다.

완료 조건: 선택한 tracker의 읽기 동작을 확인하고, 지침에서 tracker·도메인·설치된 경우 라벨 문서에 도달할 수 있어야 한다. 실제 생성·수정한 라벨과 미검증된 외부 쓰기는 구분한다. 이미 설정돼 있으면 전체 셋업 대신 바뀐 항목만 갱신한다.

## 작업 크기에 맞는 진입

| 입력 | 진입 절차 | 구현 전 완료 조건 |
| --- | --- | --- |
| 작은 수정·명확한 버그 | 요청 또는 기존 티켓 → `implement` | 기대 동작·완료 조건·관련 검증이 명확함. 별도 명세·티켓 분해 생략 가능 |
| 여러 작업으로 나뉘는 확정 기능 | `to-spec` → `to-tickets` → `implement-spec` | 명세·검증 경계 합의, 티켓 크기·의존성 승인, tracker에 연결됨 |
| 불확실한 제품·설계 결정 | `grilling`·`research`·`prototype` 중 필요한 것 → 확정 후 위 경로 | 미확정 결정과 조사 결과가 구분되고 구현 범위가 합의됨 |

모든 이름은 Matt Pocock 스킬을 뜻한다. 실제 설치된 원문의 호출 문법·사용자 확인 절차를 따른다. 이미 명세나 티켓이 있으면 원문과 댓글을 읽고 재사용한다. 초기 셋업을 이유로 제품 기능 구현을 새로 시작하지 않는다.

## 명세에서 통합 검증까지

1. `to-spec`: 대화와 코드 근거로 문제·해결·사용자 동작·구현 결정·검증 경계·범위 밖을 정리한다. 관련 용어집과 ADR을 적용하고 검증 경계를 확인한 뒤 설정한 tracker에 발행한다.
2. `to-tickets`: 명세를 각자 검증 가능한 작은 수직 작업으로 나눈다. 각 티켓에 완료 조건과 실제 선행 티켓을 둔다. 사용자와 크기·의존성을 확정한 뒤 선행 순서로 발행한다. 지원하면 tracker의 native 의존성·하위 이슈를 쓰고, 없으면 명시적인 `Blocked by`와 부모 참조를 쓴다. 이 단계에서 부모 이슈를 닫지 않는다.
3. `implement-spec`: 의존성이 없는 티켓 또는 선행 작업이 모두 완료된 티켓만 선택한다. `ready-for-agent` 라벨만으로 차단 관계를 무시하지 않는다. 선행 작업의 완료 상태와 현재 담당자를 실행 직전에 확인한다.
4. 하나의 통합 브랜치를 기준으로 작업한다. 병렬 구현이면 티켓별 브랜치·worktree와 파일 소유권을 분리하고, 시작 기준과 보고 전 통합 tip을 맞춘다. 같은 파일을 건드리는 작업은 조정하거나 순서대로 실행한다. 런타임에 하위 에이전트 기능이 없으면 같은 의존성 순서로 직렬 실행하고 차이를 보고한다.
5. 각 작업은 관련 검증을 통과한 뒤 통합한다. 통합으로 새로 준비된 작업을 선택한다. 넓은 기계적 변경은 expand → migrate → contract로 나누고, 중간 독립 검증이 불가능하면 최종 통합·검증 티켓을 둔다.
6. 통합된 최종 diff 전체에서 명세 완료 조건·회귀·작업 간 연결을 검사한다. 별도 Standards·Spec 리뷰, 확실한 결함 수정과 재검증, 권한·workflow 등 해당 영역의 Security·다른 모델 리뷰는 셋업 프롬프트 §5를 따른다.
7. 최종 head의 CI·위험별 승인·병합 기준을 확인한다. 통합 브랜치 검증과 main 반영을 구분하고, tracker의 완료 관례에 맞춰 티켓을 종료한다. 부모 명세는 전체 완료 조건을 확인한 뒤 승인된 완료 처리만 수행한다. 병합 후 main 검증과 생성한 작업용 worktree 정리까지 보고한다.
